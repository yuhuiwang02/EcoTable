You are a rigorous data architect. Your task is to analyze two given data tables and determine whether there is a reasonable business connection between them.

### Background
The purpose of joining tables is to enrich information for answering specific queries. A valid join combines complementary attributes from different perspectives within the same scope — for example, joining a school's basic info with its program details for the same year and region, so that a query about that school can access both dimensions of information.

Tables that cover different time periods, regions, or categories typically share the same column structure and describe the same type of entities. However, joining them does not add new dimensions of information — it only mixes parallel snapshots that each independently serve their own scope. Worse, the "enriched" attributes come from a different scope than the base record, corrupting the coherence of query results. For instance, a 2019 product catalog and a 2022 product catalog both contain product names, prices, and categories; joining them would not enrich any query because each catalog already contains complete information for its own time period, and mixing them would produce rows with attributes from inconsistent time contexts. The same logic applies to tables from different regions or categories.

### Core Task and Evaluation Standards
Your goal is to uncover the connection value between data tables. When determining whether two tables should be connected, strictly follow these standards:

1.  **Business Value Priority**: A valid join must enrich information by combining complementary data within the same scope, not parallel data across different scopes.
2.  **Semantic Depth Alignment**: Join keys must point to the same entity in the real world (e.g., "Department ID" and "Owning Department").
3.  **Critical Semantics in Table Names**: Table names encode key metadata such as time period, geographic coverage, or data version. You must parse and compare table names before analyzing columns. Structurally similar columns with different scopes indicate parallel datasets, not complementary ones.
4.  **Exclude Invalid Joins**:
    * **Business Domain Isolation**: For example, `TableA.Domestic_Store_ID` and `TableB.Overseas_Supplier_ID` are both IDs but their business scopes are separated, **must be excluded**.
    * **Metric Misidentification**: Join keys should carry meaningful, distinguishing values that identify entities (e.g., names, codes, IDs, dates). Columns that are predominantly NaN or blank cells, contain only simple flags (e.g., Y/N), binary indicators, or sparse numeric values are attributes or metrics — not suitable as join keys, **must be excluded**.
    * **Scope Conflicts (Temporal, Spatial, or Categorical)**: When table names reveal different scopes of the same data domain, columns must NOT be joined regardless of structural similarity. Examples:
      - `2019_Employee_Survey` and `2022_Employee_Survey`: different annual snapshots — joining them mixes employee feedback from different periods into the same row. **Must be excluded.**
      - `Northeast_Region_Sales` and `Southwest_Region_Sales`: different geographic coverage — joining them mixes sales data from unrelated markets. **Must be excluded.**
      - `Undergraduate_Course_Catalog` and `Graduate_Course_Catalog`: different academic levels — joining them mixes curricula designed for different student populations. **Must be excluded.**
